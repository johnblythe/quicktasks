# Changelog

## Unreleased

### Fixed
- A task could be left at `status: running` forever if its data directory disappeared mid-run (a fresh-install rehearsal renaming `~/.quicktasks` while a quick-fire was in flight did exactly this): `run_task` finished the Claude process fine after 8 minutes, then crashed with `FileNotFoundError` on the log append, so the task JSON was never updated past `running` and the hub feed never ran. `save()` now recreates `TASKS_DIR` and retries once if it's missing before giving up (one line to stderr, nonzero exit, only if the retry itself fails); a new `_append_log` helper does the same for the per-task log file and otherwise drops the write rather than crash a task that already finished running; and `run_task` now wraps its whole post-launch body in a safety net that stamps the task `failed` with the exception text (only if it hadn't already reached a terminal status) before re-raising, so a truly unexpected error is visible in the ledger rather than an invisible hang.
- Quick-fires' Slack guard could be routed around through a non-ld-tools MCP Slack connector (LD-224 follow-up): a headless run inherits the user's other configured MCP servers, so a Slack send denied on `mcp__ld-tools__ld_slack_send` could go out anyway through `mcp__claude_ai_Slack__slack_send_message` or `mcp__plugin_slack_slack__*`, since `SLACK_GUARD_MATCHER` only ever matched `mcp__ld-tools__ld_slack_.*` and `qt-guard.py` only judged that same prefix. `SLACK_GUARD_MATCHER` is now `mcp__.*[Ss]lack.*`, so the PreToolUse hook sees every Slack-flavored MCP tool regardless of which server it came from; `qt-guard.py` denies any of those outright with a reason naming `mcp__ld-tools__ld_slack_send` as the sanctioned path, unless `slack_allow_public_channels` is set. See README's "Slack safety" section.
- Quick-fires on a fresh install (LD-224 follow-up): a brand-new user's first quick-fire (`qt "slack me a two-line haiku about feature flags"`) came back `blocked`, denied on `mcp__ld-tools__ld_slack_user_by_email` -- headless `claude -p` runs under `--permission-mode acceptEdits`, and a fresh machine has no personal allowlist for `mcp__ld-tools__*` the way John's own `~/.claude/settings.json` does, so the very first MCP tool call any quick-fire made was auto-denied. `render_slack_guard_settings()`'s per-run `--settings` file now also carries a `"permissions": {"allow": [...]}` list (`QT_TOOLS_ALLOW`) matching the hub's own read-only `ld-tools`/`fff` allowlist (`TOOLS` in `hub/runner.py`) plus `mcp__ld-tools__ld_slack_send` and `ld_slack_user_by_email` -- not an `--allowedTools` or `--permission-mode` change, so a quick-fire keeps its normal tool freedom and the Slack guard hook still decides where a message can go. Separately, `task_prompt()` also never told the model the owner's Slack id, so "slack me" made it look the owner up by email instead of DMing a known id; the prompt now names the id directly when one is configured (hub: `owner_slack_id` from `pass-config.json`; standalone: `slack_owner_id` from qt's own config) and says Slack delivery is unavailable when neither is set. See README's "Slack safety" section.
- Quick-fires now run under a Slack guard (LD-224 incident follow-up): a quick-fire fired from the widget's ⌥Q panel posted to the public `#ask-cloud-eng` channel because `run_task`'s headless `claude -p` launch carried only `--permission-mode` -- no tool allowlist and no `--settings`, so nothing checked where an `mcp__ld-tools__ld_slack_*` call was headed. Hub-fired jobs already gate every Slack send through the hub's own `guard.py`; quick-fires had no equivalent. `run_task` now renders a one-off `--settings` file per run (under `QT_DATA/tmp`, named by the task id so two concurrent quick-fires never race on the same path, removed once the run finishes) wiring a PreToolUse hook on every `mcp__ld-tools__ld_slack_*` call -- not a tool-allowlist change, so a quick-fire keeps its normal freedom, but a deterministic gate on destinations. `resolve_slack_guard_cmd()` picks the hub's own `guard.py` (and its `pass-config.json` policy) when `qt hub <dir>` is configured and that file exists, so quick-fires obey the same policy hub-fired jobs already do; otherwise a new standalone `qt-guard.py` reads `config.json`'s `slack_owner_id` / `slack_allowed_channels` / `slack_allow_public_channels` -- read-only Slack tools always pass, every write is denied to the owner's DM or an allowed channel unless the config opts into public posting, and with no owner id at all every Slack write is denied outright rather than guessing. `qt setup` now asks for `slack_owner_id` (skipped, with a note, when the hub already governs the policy); `qt doctor` gained a "Slack guard" line naming which guard is active, the owner id in effect (or `DENY-ALL`), and whether public-channel posting is on. See README's new "Slack safety" section.
- `quicktask://resume/<id>` links built from a hub job slug (e.g. `qt-260909-165637-do-a-deep-20260909-210126`, the directory name The Pass gives a qt-originated run) resolved to nothing: `match_id()` only ever tried the raw fragment, which is never qt's own task id (`260909-165637-do-a-deep`) once the hub's `qt-` prefix and `-YYYYMMDD-HHMMSS` suffix are on it, so it exited with "no task matching" and nothing launched -- the only signal was a notification easy to miss (#4). `match_id()` now retries every candidate a hub slug could unwrap to (prefix stripped, suffix stripped, both) before giving up. When nothing still matches, `_resume-launch` no longer just exits: it appends a `resume.log` record with outcome `no-task` (the requested fragment and every candidate tried) and raises a notification naming the fragment, so a bad resume link is visible in `qt resume-log` instead of silent.
- Resume links (Slack, The Pass, menubar) opened Terminal.app instead of cmux (#3) whenever cmux's socket control mode was left at its default `cmuxOnly`, which only accepts connections from processes started inside cmux: a resume click has launchd ancestry and no TTY, so `cmux new-workspace` answered "Access denied" every time, and `_launch_cmux` treated that identically to the socket being down -- nudging `open -ga cmux` and burning the full ~10s readiness poll before falling back, when retrying could only ever be denied again. `qt doctor` also reported the terminal as healthy regardless, since doctor itself always runs from inside a cmux terminal and so never saw the denial. `_launch_cmux` now recognizes the "access denied" / "only processes started inside cmux" stderr immediately and returns a specific reason ("cmux refused an outside process (socket control mode is cmuxOnly); set cmux Settings > Automation > Socket control to password") without the app-nudge or poll, so the Terminal.app fallback is near-instant instead of ~10s. A new `_cmux_outside_probe()` reproduces the denial from `qt doctor` and `qt setup` themselves by double-forking and detaching a process to launchd (ppid 1, no TTY) before it calls `cmux ping` -- the same shape a resume click has -- so both commands now flag a `cmuxOnly` socket by name (with the `password`-mode fix) instead of reporting "socket responding" and leaving the real cause to a resume.log dig. Review follow-ups in the same PR: the post-cold-start readiness poll and the doctor/setup gate read the socket's state (ok, denied, down) instead of a bare up/down bool, so the refusal is named even when cmux was not running for the first attempt or doctor runs from a non-cmux terminal; the probe waits for launchd to adopt its child instead of a fixed sleep; cmux 0.63's broken-pipe wording of the same refusal is recognized; the remedy text lives in one constant.
- Menu-bar widget notification storm (LD-201 v9): v8 posted a "Pass isn't answering" / "Pass is back" pair on every single health transition, so an ordinary slow response under load -- one skipped poll, the Pass server never actually restarting -- read as a notification storm overnight instead of the rare real outage it was meant to catch. A Pass outage is now tracked as one continuous episode, from the first failed poll to the first subsequent success, by a new `HealthEpisodeTracker`: the "down" notification fires only once an episode has run for at least 45 seconds (`healthNotifyAfter`) or the widget has fallen all the way back to file feeds, whichever comes first, and "back" fires only if "down" actually went out earlier in that same episode. An episode that resolves before crossing that line instead produces exactly one already-seen, history-only outcome ("Pass blipped for N s") that never draws a banner and never reaches the notifier; at most one down/back pair reaches Notification Center every ten minutes (`notifyRateLimit`), anchored to the last pair actually sent, so a second outage inside that window still records its own outcomes without notifying twice. A new `JobTransitionTracker` replaces the old pairwise-only comparison with a persistent last-known-status map keyed by job id, so a job briefly missing from one poll's records and then reappearing finished still fires its outcome exactly once, deduped by the combination of job id and landed-on status rather than able to fire twice or drop silently. The reachability probe's timeout is loosened from 1.0s to 3.0s and the status-fetch timeout from 1.5s to 8s, both to stop an ordinarily slow response from reading as a failure in the first place; a poll still in flight when the next 5-second tick fires is now skipped outright rather than starting a second request on top of the first. New `--dump-notifications <seq> [--poll-interval-seconds <s>] [--hold-window-seconds <s>]` replays a comma-separated ok/fail poll sequence through both trackers on a simulated clock and reports each step's outcome plus its `episode_started`/`notified_down`/`last_pair_at` bookkeeping (286 widget tests, up from 278).
- Resume launches now log every step, and a fallback names the real reason: `_launch_in_terminal` appends one JSON record per call to `~/.quicktasks/logs/resume.log` (rotated at 200 lines) with the requested terminal, which branch ran, every subprocess argv/rc/stderr it tried, elapsed time, and a final outcome (`cmux`/`ghostty`/`custom`/`terminal-forced`/`terminal-fallback`); `qt resume-log [n]` prints recent entries. A cmux fallback notification used to say only "cmux unreachable" no matter what actually happened -- it now says which of three specific things went wrong ("cmux CLI not found", "cmux socket not answering after 10 s", or "cmux new-workspace failed (rc N): <stderr head>"), and `CMUX_QUIET=1` is now passed on every subprocess call that talks to cmux, not just some of them.
- `qt install-handler` and `qt uninstall-handler` now sweep every other LaunchServices bundle claiming `com.quicktasks.resume-handler` (parsed read-only from `lsregister -dump`) before touching their own, printing what they removed -- previously only the one known app path was ever unregistered, so a stale duplicate from an old build (or a defunct staging path) could keep silently winning a resume click. The handler's baked `do shell script` now also carries `CMUX_QUIET=1` and an extended PATH (`/opt/homebrew/bin:/usr/local/bin:$HOME/.local/bin`), since a clicked link's shell doesn't inherit the interactive PATH cmux is usually found on. `qt doctor` gained a "resume handler" section: every claimant of the identifier and which one is installed, the interpreter and qt path baked into it (and whether both still exist), the configured terminal and what `find_cmux()` resolves to under that same bare PATH, and the last few `resume.log` records.
- `find_claude()`'s cmux-shim rejection matched "cmux" as a raw substring anywhere in the resolved path, not just as its own path segment -- so a checkout whose own directory name merely happens to contain those four letters (any `-cmux-` discovery worktree, for instance) had every `claude` on its PATH rejected in favor of a real system install, silently defeating a test's fake-claude shim. It now only rejects "cmux" as a whole path segment (`.../cmux/...`, `.../cmux-workspace-1/...`), not a substring of an unrelated directory name.
- Menu-bar widget v8, "never an unsure moment" audit (LD-201 v8): the single `flash` string, which vanished the moment the dropdown closed, is replaced by a persistent outcome queue -- quick-fire, a row action, the login-item toggle, a Restart Pass verdict, Settings Apply, and a Pass health change now all write an `Outcome` (ok/error/info) that survives the dropdown closing and a relaunch, capped at the last 20. The newest unseen outcome draws as a dismissible banner at the top of the row list ("Fired: <text>", "Accepted", "Job finished: <title>", or an error in red with the reason) and is marked seen, not deleted, after about two seconds visible, with earlier ones folding under "N earlier" so a burst of several is never lost the moment the newest is dismissed or ages out. A new Settings toggle, "Notify me when the dropdown is closed" (on by default), posts those same outcomes as real macOS notifications while neither the dropdown nor the summon panel is open, through one `Notifier` protocol -- `SystemNotifier` for the running app, `RecordingNotifier` for every test and snapshot, so nothing in the suite or a CLI seam can ever reach Notification Center -- requesting authorization exactly once, on the toggle's off-to-on edge. A login-item toggle failure now reverts the switch and posts the reason instead of silently un-checking it; the toggle's real success and forced-failure paths are both now testable via `QT_MENUBAR_LOGINITEM_FORCE_OK`/`_FORCE_FAIL` rather than a real `launchctl` round trip. The menu-bar dot gains a second signal independent of its running/attention/idle colour: a small notch for holding a stale Pass read, a hollow ring for having fallen back to file feeds, both named outright in the hover tooltip so the shape and the words can never disagree. A new always-visible footer line says how long ago that state was confirmed -- "synced 12 s ago", "holding since HH:MM", or "file feeds · Pass down since HH:MM". New `--dump-outcomes <seq>` drives every producer above against a real, headless controller and reports the resulting queue, notification log, and authorization-request count (290 widget tests, up from 252).
- Menu-bar widget summon focus (LD-201 v7): pressing the global hotkey opened the panel but keyboard focus landed in the quick-fire field only on the very first summon -- the reused `NSHostingView` never re-ran `.onAppear`, SwiftUI's one-shot-per-lifetime hook, so every summon after that left the field showing but untypable until a click. A new `summonTick` counter is bumped on every summon and observed by the view, re-running the same focus routine `.onAppear` used to run alone: the panel is activated and made key first, then `@FocusState` is set once on the next run-loop turn and again ~50ms later, since SwiftUI drops a focus write made before its window is actually key. `⏎` now fires with the current mode and then hides the panel; a second summon while showing, or Escape, still hides it as before. The quick-fire field also gained firing/fired/failed states, shared by the summon panel and the real dropdown since both host the same view: while sending it disables and shows "Firing…" (Run now) or "Sending to the Pass…" (To Pass); on success it shows "Fired: <first 40 characters>" or "On the Pass: <full text>" for ~1.2s, then clears (and, in the summon panel only, hides); on failure the typed text stays and the refusal shows in red under the field. New `--dump-summon` (drives the real hotkey/Escape code path headlessly) and `--dump-fire-outcome` (computes the exact on-screen state and message a fire produces, via the same pure `FireFieldOutcome.describe()` the view calls) make both testable without a display (252 widget tests, up from 239).
- Menu-bar widget headline flap (LD-201 v6): the panel's task count could flip between two different numbers on consecutive 5-second polls -- a restart race or a leftover test server rewriting `.pass-url` to a stray port got trusted over a healthy default-port Pass, and a single slow poll on the (single-threaded) Pass server fell straight back to the file ledgers' own count. Discovery now tries `http://127.0.0.1:8811` before `.pass-url`, and only trusts the file once its `/status.json`'s `instance.hub_dir` (realpath-resolved) matches the widget's own configured hub -- a mismatch is reported by name (`rejected: "<url> serves <other dir>"`) rather than treated as unreachable; a payload with no `instance` field at all (an older Pass) is accepted only once 8811 has failed. `QT_PASS_URL` is unchanged: authoritative, never falls back. A failed poll after at least one Pass success now holds the last successful model for up to 90 seconds instead of falling back immediately -- the footer dot turns amber with a tooltip reading "Pass unreachable since HH:MM · showing HH:MM" -- and only once that window runs out does the headline read "... · file feeds only, Pass down". Recovery snaps back on the very first successful poll, mid-hold or after the window has already expired. New `--poll-sequence`/`--poll-interval-seconds` seam on `--dump-model` replays a whole run of polls against a synthetic clock so the hold's timing is covered without a real 90-second test (239 widget tests, up from 227).
- Menu-bar widget discovery (LD-201): a `.pass-url` naming a target that stopped answering used to be trusted blindly, so a Pass that died on its old port could leave the widget reporting a URL nothing is listening on instead of falling back the way a missing file does. Discovery now probes a `.file`-sourced result with one loopback `GET /status.json` and falls back to port 8811 when it does not answer, while `QT_PASS_URL` stays authoritative and is never second-guessed. The footer tooltip and `--dump-endpoint` still show the raw file contents alongside whichever address was actually used, so a fallback never looks identical to a live read.
- Menu-bar widget, corrections against a real `/status.json` body (LD-201): the verdict buttons now key off the item's `state` rather than its reason, so a job that died in the verify lane still offers accept / redo / reject instead of only reading "Failed"; a job with no `started` falls back to `generated_at` for ordering only, so rows the Pass reports without timestamps still sort and still count as today instead of dropping behind the collapsed Earlier section, while never being given an age they do not have; capture text over 4000 characters is refused in the widget's own words rather than sent for a 400; and empty Pass groups no longer pad the header tooltip. The real payload omits `title`, `started`, `elapsed_s`, `failed`, `blocked`, and `session_id` from jobs that have nothing to say about them, so it is now pinned as a verbatim regression fixture (96 widget tests, 103 in the repo).
- Task ids now carry the year (`yymmdd-hhmmss-slug`) and get a numeric suffix on same-second collisions, so a same-second queue can no longer overwrite an existing task and filename order survives New Year.

### Added
- `qt setup --defaults [--hub <dir>]`: a non-interactive path for scripted installs like the hub's one-command installer, since plain `qt setup` always reads from stdin. Writes `permissions` (`acceptEdits`), `model` (`sonnet[1m]`), and `terminal` (the same auto-detected choice interactive setup offers as its default) with no prompts; `--hub <dir>` turns the hub feed on for that dir exactly like `qt hub <dir>` does, validating `serve.py` is present, and leaves `slack_owner_id` unset since a configured hub's own `guard.py` governs Slack policy instead. Omitting `--hub` leaves the hub feed off. Idempotent: a rerun only touches the keys above, leaving `trusted_dirs`, `notifier`, `trusted_permissions`, and any existing `slack_owner_id` exactly as they were.
- Quick-fire origin and hub-owned auto-close (LD-224): every task now carries an `origin` -- `qt`, `raycast`, `widget`, or `summon` -- read once from `QT_ORIGIN` at queue time and falling back to `qt` on anything unset or unrecognized; both Raycast surfaces (`quick-task.sh`, the `lib.ts` extension) and the widget's dropdown/summon-panel fire path now set it. That origin rides along into the hub job's own JSON, so a future Verify-lane decision can tell a CLI quick-fire from a widget or hotkey-panel one apart. After writing that job and before the finish notice, `_feed_hub` now also shells out to the hub's own `deliver.py` against the jobdir it just wrote, exactly the way it already does for `notice.py`: a missing script is a silent no-op, the call is capped at 10s, and a failure logs under its own line rather than raising -- so the hub alone decides whether a delivered job auto-closes to Done, and qt never has an opinion about it. The menu-bar widget gains a Revive row action for any item the hub marks `revivable: true`, posting `{"id": "<item_id>"}` to a new `POST /revive`; an older hub with no such route (404) reads as a plain action error like any other rather than something special-cased, the way `/run`'s 409 is. A revivable done job still sorts into Done today with no new section, and file-mode ledgers (no Pass feed) never offer the button, the same way they never offer Run it. New CLI seams `--dump-revive` and `--post-revive` mirror `--dump-run`/`--post-run` for the request body and the real round trip (297 widget tests, up from 286).
- Menu-bar widget v5 (LD-201): quick-fire gains keyboard shortcuts and a directory chip. `Tab` flips the remembered Run now / To Pass toggle without touching the field; `⌘1`/`⌘2` select a mode directly; `⌘⏎` fires with whichever mode is *not* selected, once, without moving the remembered default -- the hint caption under the field ("Tab swaps · ⌘⏎ fires the other way") says so up front. A global summon hotkey, `⌥Q` by default and recordable or clearable in Settings, opens quick-fire from anywhere through Carbon's `RegisterEventHotKey` rather than `NSEvent.addGlobalMonitorForEvents`, so it needs no Accessibility or Input Monitoring permission; since `MenuBarExtra` has no supported way to trigger its own dropdown from code, the summon key opens a separate floating panel hosting the same view instead, leaving the real dropdown untouched. Run now gains a directory chip next to the toggle, showing and letting you change the working directory a fire will use, with a recency menu built off the eight most recent `run_cwd` values in the `qt` ledger; a typed `--in <dir> ` or `@<dir> ` prefix fires that one time in `<dir>` without touching the chip's own remembered choice, and resolves ahead of `QT_MENUBAR_FIRE_DIR`, which still outranks the chip. To Pass ignores the chip and any typed prefix outright, since a gate item has no directory field to put one in. New CLI seams `--dump-fire`, `--dump-hotkey`, and `--dump-recent-dirs`, plus `tab`/`cmd-1`/`cmd-2`/`cmd-return` tokens on `--dump-keys`, make the mode flip, the fire resolution, the hotkey registration, and the recency list testable without a display or a real keypress (215 widget tests, 227 in the repo).
- Restart Pass (LD-201): the previously-disabled settings-window button now works, POSTing `/restart` behind a confirmation sheet ("Jobs in flight keep running; the page and this widget reconnect in a few seconds."). A launchd-supervised Pass reports `supervised: true` and the sheet polls `/status.json` for up to ~20s before saying "Pass is back"; a hand-started one reports `supervised: false` and the sheet says how to start it again by hand rather than implying it will return on its own. A Pass old enough to predate the route (404) leaves the button enabled and says so instead of disabling it, since the reason changes and the remedy does not; an Origin the gate refused (403) reports the refusal. New CLI seams `--dump-restart` and `--post-restart` mirror `--dump-run`/`--post-run` for the request and the real round trip (190 widget tests, 202 in the repo).
- Slack finish notices (LD-211): a finished task now also asks the hub to raise a Slack notice, so a result no longer rides solely on an ephemeral desktop notification that macOS can silently drop. `_feed_hub` invokes the hub's own `notice.py` against the jobdir it just wrote, and that script owns the entire policy -- blocked, failed, and timed-out runs always post; a success posts only past a duration threshold, since the menu-bar widget already covers the at-desk case -- so qt decides nothing about notification and the two repos cannot drift apart. A missing `notice.py` is a silent no-op like the rest of hub mode, the call is capped at 10s because it sits ahead of the local notification on the finish path, and a notice failure logs distinctly from a feed failure: by the time it runs the item, `job.json`, and `RESULT.md` are already on disk, so pointing a future debugger at the feed would send them to the wrong subsystem.
- Menu-bar widget v3, against The Pass's `/status.json` v2 (LD-201): rows gain the four things the payload now tells them. **Run it** fires a gate item's own kickoff prompt through `POST /run`, offered only where the server says `can_run` (a non-empty prompt, and a lane that is not already running or awaiting a verdict), asking first the way reject does, since it spends one of three job slots; a 409 is an answer rather than a fault and reads as "Already running" or "Job slots full, not fired" instead of an HTTP status. **Titles deep-link** to the item through `item_url_template`, falling back to the Pass root on a v1 payload or a task The Pass has not heard about yet. **Done today is decided by `finished`** rather than by `started + elapsed_s`, which the v1 reconstruction only approximated, and a `truncated` payload says so in the footer with the real job total. **`needs_you` is now self-sufficient** -- it carries its own `resume_url`, `report`, `session_id`, `started`, and `can_run` -- so a row whose job was capped out of `jobs` still resumes with its report, and a gate item finally has a real age instead of borrowing `generated_at` for ordering; the join onto `jobs` still supplies `elapsed_s`, `outputs`, `error`, and the denial count, with the `needs_you` entry winning any field both sides send. Titles come from the payload everywhere now, keeping the id fallback only for an empty one. **The Pass is discovered rather than assumed**: `QT_PASS_URL`, then the hub checkout's `.pass-url` that `serve.py` writes on bind, then port 8811, with a discovered URL required to be http on loopback and a malformed one reported in the footer tooltip and ignored. **Keyboard basics**: up and down move a highlight through the visible rows without wrapping, return takes the highlighted row's primary action (resume, else the deep link, never a verdict or a fire), and escape clears the quick-fire field. New CLI seams `--dump-endpoint`, `--dump-run`, `--dump-keys`, and `--post-run` make discovery, the run body, the keyboard, and the 409 wording testable without a display. Every v2 field is optional on the way in, so a v1 payload still parses and is still pinned as a verbatim fixture alongside the new one (155 widget tests, 162 in the repo).
- Menu-bar widget v2 (LD-201): the widget becomes the front door to the whole loop, not just to `qt`. It now polls The Pass's `GET /status.json` every 5s and falls back to the file ledgers when nothing answers, with a footer dot saying which feed is live and why, because "all quiet" and "I cannot see The Pass" must never look the same. Rows group into collapsible sections (Running, Needs you, Done today, Earlier) whose collapse state is remembered, with Needs you ordered verify, gate, blocked, failed; `needs_you` entries are joined onto `jobs` by `item_id`, so a held gate item with no job still gets a row whose reason is its status text. Verify rows get inline accept / redo / reject that post the review page's own `POST /save` body, with redo taking a note inline and reject asking first; any unreconciled decision in the hub's `decisions.json` rides along, since `serve.py` overwrites that file wholesale. Rows also gain a report button that opens `pass_url` plus the job's `report` path, and in-flight rows show elapsed time ticking every second off the wall clock. Quick-fire gains a remembered Run-now / To-Pass toggle, the second half posting `POST /capture` to file the text as an item needing a go. The footer gains a "Start at login" switch that writes and boots the same LaunchAgent `build.sh --agent` does, from the same template, now shipped inside the app bundle. Even in Pass mode the qt ledger is still read and merged, so a task fired seconds ago appears before The Pass knows about it. New CLI seams `--dump-capture` and `--dump-decision` print the two request bodies without sending them. 82 tests, including a real loopback fixture server for the Pass path.
- macOS menu-bar widget (LD-201): a native `MenuBarExtra` app in `menubar/`, built by `./build.sh` with `swiftc` alone (Command Line Tools, no Xcode project, no runtime dependencies), so `qt` no longer needs Raycast to be usable. The menu-bar icon is a coloured dot plus count for aggregate state (blue running, orange needs-you, grey quiet); the dropdown has an inline quick-fire field that shells out to `qt <prompt>`, one row per recent run with a status dot and one-click resume through the existing `quicktask://resume/<id>` handler, and a refreshed-at footer with buttons for The Pass, refresh, and quit. Reads and deduplicates both ledgers (`~/.quicktasks/tasks/` and the hub's `jobs/`) keyed on the id `qt resume` accepts, so a Pass job still in flight appears before it is mirrored back; blocked and failed runs pin above successful ones, and a run with no session id shows no resume affordance rather than a dead click. Polls every 5s off the main thread; no network beyond `127.0.0.1`. `./build.sh --agent` installs a LaunchAgent so it starts at login (`KeepAlive` off, so the quit button is a real quit). Also a small CLI: `--dump-model` prints the computed menu model as JSON and `--snapshot` renders the dropdown to a PNG with no Screen Recording permission needed.
- Slack resume footer: tasks are told their own id and instructed to end any Slack message they post with `qt resume <id>` plus a `quicktask://resume/<id>` link.
- `qt install-handler` / `qt uninstall-handler`: register or remove a macOS `quicktask://` URL handler (applet in the qt data dir, qt path and `QT_DATA` baked in, no Dock icon) so resume links in Slack open the session in the preferred terminal. Link ids are validated to lowercase letters, digits, and hyphens before any shell call; install reports codesign and LaunchServices registration status honestly and stages rebuilds so a failure cannot destroy a working handler.
- `qt doctor` verifies the handler bundle, its scheme, and its signature.
- `qt setup` gained a default-model step: `sonnet[1m]` (Claude Code 2.1.266+'s 1M-context alias) is offered as the recommended choice for qt's longer unattended runs, or you can pick "unset" or type any other model/alias. Pressing Enter without choosing changes nothing -- a configured model stays configured, and staying unset keeps falling through to the `claude` CLI's own default rather than setup quietly forcing a choice on anyone who skips it.
- `qt resume-log [n]`: prints the last n resume-launch records (requested terminal, branch, outcome, rc, elapsed time, stderr head) straight from `resume.log`.

Off by default and a strict no-op until configured; the feed itself can never fail a task, only log to it. `qt hub off` / `qt hub status` clear or inspect it, and `qt doctor` reports whether it's configured and reachable.
